## Phase 1 — Individual accounts and resource ownership

**Included in the accompanying patch; must be validated in the target repository before merge.**

- Password hashing with Node.js `scrypt` and constant-time hash comparison.
- Server-side sessions: only SHA-256 token hashes are stored in PostgreSQL; the browser receives an HttpOnly, SameSite=Lax cookie.
- Login, registration, logout, session inspection, login/registration rate limiting, and a same-origin mutation guard.
- Ownership on datasets, evaluation runs, and campaigns; API repository operations are scoped to the authenticated owner.
- Existing v1.0 data remains ownerless during migration and can be claimed by the first account only after providing the configured bootstrap secret. The claim runs transactionally.
- Registration is disabled by default in Docker Compose; enable it deliberately for initial local account setup, then turn it off when the intended accounts exist.
- Restrictive Content Security Policy defaults and loopback-only published dashboard/database/Redis ports.

Acceptance:

1. Existing database upgrades without losing datasets, dataset versions, runs, results, campaigns, or audit events.
2. Unauthenticated resource API requests return 401.
3. A second account cannot list, view, edit, compare, or cancel another account's dataset/run/campaign, including by guessing a valid UUID.
4. Failed bootstrap-secret validation creates no user and claims no legacy records.
5. Password and auth/session tests, `npm test`, and `npm run test:regression` pass.
6. The browser login flow, session expiration, logout, cookie settings, and two-user isolation are verified manually in Docker Compose.

## Phase 5 — Cost and provider accuracy

Implemented and locally verified (2026-10-18). Per-call cost snapshots include the actual answering model, including generation fallback and LLM judge calls; configured rates, pricing source/effective date/tier/assumptions, provider service tier, and capture timestamp are persisted in the result metadata. OpenAI cached input and Gemini cached input, reasoning/thought, tool-use prompt, total, and modality detail fields are retained. Cached input is charged separately only when its cached rate is configured; unknown cached prices and Gemini tool-use prompt pricing produce an explicit partial total and a known subtotal. OpenAI reasoning tokens remain a detail of output tokens and are not double-counted. Provider-wide cached-input rates are configurable, model-specific rates can carry provenance metadata, and no public provider prices are hard-coded. Tests cover model/provider rates, fallback model attribution, cached and unsupported categories, explicit zero, incomplete rates, partial totals, and persisted historical snapshots. Local `npm test` passed (190/190), `npm run test:regression` passed (8/8), focused cost/provider/runner tests passed (52/52), and `git diff --check` was clean. GitHub Actions has not yet run for this Phase 5 working-tree change; live provider pricing/usage was not exercised, so account-specific billing remains to be confirmed from actual provider billing records.

- Keep per-call usage and pricing snapshots attached to the actual responding model, including fallback and judge calls.
- Record pricing source, retrieval/effective date, tier and assumptions, where known.
- Handle provider-reported cached-token and other billable categories when the API supplies sufficient data; keep unsupported categories explicit.
- Keep costs unavailable when the required rate or usage components are unknown; never silently convert missing cost to zero.

Acceptance: tests cover model-specific and provider-wide rates, fallback-model attribution, cached/extra usage fields when available, explicit zero rates, incomplete rates, partial totals, and historical snapshots.

## Release rule

A phase is not considered complete solely because its files exist or syntax checks pass. It is complete only after its automated tests pass, migration/upgrade paths are exercised, manual acceptance checks are recorded, documentation is accurate, and the resulting commit passes GitHub Actions. Do not describe this branch as production-ready until the security and operational acceptance checks are independently verified.
